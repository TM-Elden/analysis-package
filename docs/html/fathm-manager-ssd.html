01 · proof already in hand

I automated the full SSD forecast by talking to a chatbot.

Upstream, logic, downstream - end to end.

  • UpstreamAll source data given to the agent.
  • In-betweenForecast logic taught in conversation / instructions.
  • DownstreamEvery report specified - the agent builds them.

That works. Clawbot-style adoption is mixed across the team - this is the high end of what’s already possible on a real commodity.

02 · the cost of waiting

Every cycle we publish without capturing it, we throw the alpha away.

For an AI-native room

Every day we wait, alpha walks out of the building and into the trash - we pay for the decision once, then throw away the metadata that made it.

The planner’s real product isn’t only the forecast tab. It’s the decision apparatus: which sources counted, what was overridden, why the hold, what truth got applied.

That evaporates into chat scrollback and tribal memory. We fund the judgment - then store almost none of it in a form agents or leaders can use again. Cash and data, both on fire.

We burnHow
CashSame judgment re-earned next cycle; audit and rebuild tax
DataIrreplaceable human deltas never land in a queryable corpus
AI-native futureLeaders can’t ask the team’s work; bots can’t learn our standards safely

For a skeptical operator: we’re already paying planners and bots. Without packages, we pay again next week for the same archaeology - and we still can’t answer where the number came from.

03 · the tension

Two goals that look like they conflict.

Move fast with agents

Real, nonstandard planning work - draft at chat speed on the SSD loop we already proved.

AI-native + auditable

Traceability / lineage. Leaders (e.g. Curran, Ashwini, Gaia) can ask any question of our analysis - and trust the answer.

Chat-only drafts fight the second goal

We needChat-only gives us
LineageBroken or manual
DQ checksAd hoc

GovernanceAfter-the-fact
Query across the teamThreads + drive archaeology

Question: How do we get lineage, quality gates, queryability, standardization, and governance across nonstandard processes - without killing agent speed?

04 · enter fathm

Understand every analysis fully, down to its source.

For this pilot, fathm is three things:

  • PackageThe publish unit - inputs + as-of, method, outputs, human overrides with credit, QA.
  • GateDoesn’t count as published until complete.
  • Chart roomManagers and leaders query validated packages with citations.

Agents stay the draft surface. Packages are how drafts become institutional.

Agent draft→ Human judgment→ Package→ Gate→ Chart room

05 · two beats · one pilot

Surface first. Then make it scalable.

BeatWhatSuccess signal
A · Surface Agent is default draft path for the SSD forecast loop Most cycles start in the approved agent surface - not shadow one-offs
B · Scale Every in-scope publish is a gated package 100% packages with queryable lineage; sponsor queries weekly

A without B

Faster unauditable sludge. Alpha still in the trash.

B without A

Process with no traffic. Empty chart room.

Appendix · presenter only

Delivery notes and objections.

  • Lead with SSD proof - not brand mythology
  • Say fathm once; if the name distracts, “analysis package pilot” is fine
  • Name leaders only if it fits culture; else “leadership can query”
  • Bring one ugly artifact: chat → final report with no lineage link
  • Offer kill criteria unprompted
  • Clawbot: “channel mixed adoption,” not “everyone must use X”

If they push back

“Just use our catalog / DQ tool”

Wrong grain - those are tables and pipelines. This is the analysis publish unit bots create.

“Agents aren’t ready”

Mixed adoption is already here; the SSD loop shows the upside. We’re governing reality.

“More process slows us”

Gate is the minimum to call it published. Draft stays as fast as chat.

“Are you building a startup at work?”

Internal pilot so this team is AI-native and auditable. That’s the whole ask.

“Planners will hate it”

Overrides keep credit; less rebuild next cycle. Judgment stays human.
